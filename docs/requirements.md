# Requirements specification — Phase 3

**Product:** Aexa — Adaptive Explainable AI-Driven Observability Platform  
**Document status:** Phase 1 foundation, Phase 2 telemetry, and Phase 3 ML analysis
**Environment inspected:** Windows 11, Java 21.0.9 (Temurin), Maven 3.9.11, Node.js 22.12.0, npm 10.9.0, Python 3.13.3, Docker Desktop 4.97.0 with WSL 2.

## 1. Problem statement

Cloud-native microservices fail in ways that are hard to reconstruct from a single signal. Operators need correlated metrics, logs, and traces; early warning of degradation; ranked investigation hypotheses; and human-readable explanations — without allowing automated systems to change infrastructure without limits.

## 2. Goals (project)

| ID | Goal |
| --- | --- |
| G1 | Collect and correlate metrics, logs, and traces with shared identity and time. |
| G2 | Monitor health, latency, throughput, errors, and resource use. |
| G3 | Detect abnormal behaviour with a baseline method and at least one evaluated ML method. |
| G4 | Forecast selected SLO-related metrics over a defined horizon. |
| G5 | Rank plausible root causes across a dependency graph, with evidence, without claiming causation. |
| G6 | Explain detections and predictions in operator language, including model limits. |
| G7 | Adapt sampling/collection within min/max bounds, cooldowns, and audited policy. |
| G8 | Provide an investigation dashboard and incident history. |
| G9 | Measure detection quality, forecast error, investigation time, and monitoring overhead against a documented baseline. |

## 3. Phase 1 scope (historical; foundation completed)

Phase 1 delivers the **engineering foundation**, not anomaly models or live telemetry pipelines.

**In scope**

- Requirements, architecture, data-flow, technology plan, API and database design.
- Repository layout for backend, frontend, ML service, infrastructure, and documentation.
- Spring Boot orchestration API with health, security skeleton, error model, Flyway schema, and catalog/incident persistence.
- React TypeScript dashboard shell using the project visual theme.
- Initial FastAPI ML health endpoint (superseded by Phase 3 inference service).
- Docker Compose definition for PostgreSQL.
- Local Windows run path with H2 profile.
- Automated backend, frontend, and ML health tests.

**Out of scope at the Phase 1 milestone**

- AI modeling, forecasting, SHAP/LIME, RCA ranking.
- Anomaly detection, forecasting, SHAP/LIME, RCA ranking.
- Adaptive sampling actuation against collectors.
- Kubernetes production manifests beyond a placeholder folder.
- Claims of MTTR reduction or accuracy numbers.

## 4. Functional requirements

### 4.1 Cross-cutting identifiers

| ID | Requirement |
| --- | --- |
| FR-ID-1 | Every persisted domain record uses a UUID primary key generated by the application. |
| FR-ID-2 | All API timestamps are ISO-8601 in UTC (`YYYY-MM-DDTHH:mm:ss.sssZ`). |
| FR-ID-3 | Telemetry correlation uses OpenTelemetry `trace_id` (32 hex chars) and `span_id` (16 hex chars) when present. |
| FR-ID-4 | Service identity uses `service.name`, optional `service.namespace`, `service.version`, `deployment.environment`, and `service.instance.id`. |
| FR-ID-5 | Every HTTP request logs a `X-Correlation-Id` (accepted or generated). |

### 4.2 Platform capabilities (full project)

| ID | Module | Requirement |
| --- | --- | --- |
| FR-TEL-1 | Ingestion | Ingest metrics, logs, and traces with consistent timestamps and service identifiers. |
| FR-MON-1 | Monitoring | Expose service health, latency, throughput, error rate, CPU, memory, network, and dependencies. |
| FR-ANM-1 | Anomaly | Baseline plus one evaluated ML detector; configurable thresholds; documented cold-start and missing-data behaviour. |
| FR-PRD-1 | Prediction | Forecast whether selected metrics may breach a threshold within horizon *H*; distinguish forecast vs anomaly vs incident. |
| FR-RCA-1 | RCA | Rank candidates from metrics, logs, trace dependencies, and time; ranking scores are not probabilities or causal proof. |
| FR-XAI-1 | Explainability | SHAP or LIME feature influence with supporting telemetry and stated limitations. |
| FR-ADP-1 | Adaptive control | Adjust collection interval or trace sampling within min/max, cooldown, safe defaults, and audit log. AI cannot apply unrestricted infra changes. |
| FR-INC-1 | Incidents | Status, severity, affected services, timeline, evidence, suggested steps, history. |
| FR-UI-1 | Dashboard | Overview, service explorer, telemetry, anomaly timeline, predictions, investigation, adaptive settings, incident history. |

### 4.5 Phase 3 AI analysis requirements

| ID | Requirement | Acceptance |
| --- | --- | --- |
| P3-FR-1 | Prepare sorted UTC one-minute features, aggregate duplicate timestamps, forward-fill at most two missing minutes, and fit imputers/scalers on training data only. | Leakage and gap tests |
| P3-FR-2 | Compare a past-only robust rolling median/MAD baseline with a RobustScaler + Isolation Forest detector using a chronological holdout. | Saved evaluation metrics: precision, recall, F1, false-positive rate, incident detection delay |
| P3-FR-3 | Predict p95 latency >= 1.0 seconds within five one-minute samples; compare a class-weighted Random Forest to a persistence baseline using chronological validation with a five-minute boundary gap. | Saved classification metrics |
| P3-FR-4 | Explain detector and forecast outputs with LIME local surrogate feature contributions. | Explanations are derived from model outputs and carry limitations; no arbitrary confidence |
| P3-FR-5 | Rank RCA candidates from supplied metrics, actual trace edges, service identity, time-windowed logs, and pre-incident baselines. | Ranked evidence; `causality_confirmed` remains false |
| P3-FR-6 | Expose bounded, timezone-validated FastAPI schemas and authenticated Spring proxy APIs; fail explicitly on unavailable model, timeout, or invalid request. | Python and Spring API tests |
| P3-FR-7 | Generate reproducible normal/failure/noisy/missing/irregular datasets and preserve evaluation plus model metadata. | Fixed seed, data hash, tests, saved JSON |

## 5. Non-functional requirements

| ID | Category | Requirement |
| --- | --- | --- |
| NFR-1 | Security | No secrets in git. Env-based config. Passwords hashed (BCrypt). JWT for API. RBAC on mutating admin actions. |
| NFR-2 | Reliability | Explicit failure handling; health shows DB down; telemetry upstream failure returns an explicit 503, never fabricated metrics. |
| NFR-3 | Operability | Structured logs (timestamp, level, logger, correlation id, message). |
| NFR-4 | Maintainability | Layered packages, OpenAPI, Flyway, meaningful names. |
| NFR-5 | Testability | Unit + slice/API tests for backend; component tests for frontend; pytest for demo and ML services. |
| NFR-6 | Portability | Windows PowerShell commands documented; Docker Compose for Linux containers when Docker is available. |
| NFR-7 | Performance | Not measured in Phase 1. Later: document ingestion throughput and API latency against a baseline. |
| NFR-8 | Honesty | Synthetic or catalog seed data is labelled. No invented accuracy or MTTR claims. |

## 7. Assumptions (Phase 1)

1. Docker is not available on the inspected development machine; Compose files are implemented but cross-container verification is pending.
2. Local PostgreSQL 16 is installed but the `postgres` superuser password is unknown; Phase 1 default runtime profile is **H2** so the foundation can be verified without that password.
3. Canonical production-like store is **PostgreSQL 16**; H2 is a development/test stand-in (`MODE=PostgreSQL`).
4. Kafka, Prometheus, Loki, Jaeger, and the OTel Collector are Phase 2 local Compose dependencies.
5. Python 3.13 is used for the Phase 1 health service. Later ML libraries (SHAP) may require documenting a 3.11/3.12 venv if wheels are incompatible — decision deferred until the modelling phase.
6. The visual theme from the provided dashboard reference (mint canvas, teal navigation, pastel KPI cards, large radii) is the **mandatory UI language** for every frontend screen.

## 8. Out-of-scope claims

The platform will not, in Phase 1, detect incidents, predict breaches, or reduce operator workload. Those outcomes require later implementation **and** measured evaluation.
