# Independent Research Validation and Technical Review

**Project:** Adaptive Explainable AI-Driven Observability Platform for Predictive Performance Monitoring and Intelligent Root Cause Analysis in Cloud-Native Microservices  
**Review date:** 2026-10-27  
**Review scope:** Repository inspection, evidence review, automated tests, and read-only local runtime checks. No application source code was changed.  
**Overall finding:** A substantial local demonstrator is implemented and its core tests pass. Phase 5 is **not complete** against its stated verification criteria. The evidence supports functionality on synthetic/local workloads, not production quality, causal accuracy, reduced overhead, reduced investigation time, or scientific novelty.

## 1. Executive assessment

The project has an end-to-end local telemetry path, authenticated Spring APIs, a React dashboard, a Python inference service, persistent anomaly/forecast history, and a bounded demo-service trace-sampling controller. The telemetry path was live during this review: the authenticated backend returned metric, log, and trace data.

The strongest quantitative evidence is a deterministic synthetic holdout and a deterministic adaptive replay. On the synthetic forecasting holdout, the Random Forest exactly ties the current-latency persistence/threshold baseline. On the anomaly holdout, the statistical baseline has better F1 and a lower false-positive rate than Isolation Forest. The adaptive replay reduces a *sampled-span count proxy* while retaining detection in its six intentionally clear synthetic incidents. None of those results establishes behavior on production or labeled real incidents.

Phase 5 remains incomplete because:

- No labeled real-incident dataset or configured Kubernetes cluster is available (confirmed by the project owner).
- Forecast calibration and performance against a static alert baseline have not been established beyond the existing persistence comparison.
- RCA ranking has no measured top-1/Recall@k/MRR against known causes.
- Adaptive collection has no measured CPU, memory, network, storage, or telemetry-loss comparison.
- Investigation time, navigation steps, and diagnosis correctness have not been measured in a controlled user study.
- The Compose demo-service healthchecks time out even though direct service health endpoints respond `UP`; the stack is therefore not wholly healthy by Docker's health status.
- Several documents and the capability contract disagree with the actual implementation.

This is an engineering integration project with potentially useful project-specific combinations and workflows. The inspected evidence does not establish a novel algorithm or a research contribution beyond implementation and evaluation of existing methods.

### Actual data flow

1. The traffic generator calls `checkout-api`, which calls `inventory-api`, which calls `pricing-api`. These services emit OpenTelemetry telemetry.
2. The Collector exports metrics for Prometheus scraping, logs to Loki, traces to Jaeger, and signals to Kafka topics.
3. React calls authenticated Spring APIs. Spring queries Prometheus for metrics, Loki for logs, and Jaeger for traces.
4. Anomaly/forecast run endpoints fetch recent Prometheus observations, proxy validated windows to FastAPI, and persist returned anomaly/forecast records and explanations in PostgreSQL.
5. The investigation UI independently fetches metrics, logs, traces, and catalog metadata, converts returned spans to dependency edges, and submits the evidence to the Spring ML proxy. RCA is a caller-driven analysis, not a background incident detector.
6. Adaptive control obtains risk signals and applies bounded trace-sampling changes through the demo services' runtime sampler interface. It does not change Prometheus scrape intervals.

The detailed source/config path is documented in [`telemetry-data-flow.md`](telemetry-data-flow.md), with the persistence caveat below.

## 3. Inconsistencies and review findings

1. **Persistence documentation is stale.** [`telemetry-data-flow.md`](telemetry-data-flow.md) says analysis results are not persisted, but `HistoricalAnalysisService` writes anomaly/forecast outputs and explanations. RCA remains unpersisted.
2. **Adaptive capability contract disagrees.** [`PlatformController.java`](../backend/src/main/java/com/aexa/platform/api/PlatformController.java) returns `adaptiveControlActuation=true`, while the example in [`api-contracts.md`](api-contracts.md) says `false`. The actual capability is limited to demo-service sampling and must be described with that scope.
3. **Phase/status documentation is stale.** [`README.md`](../README.md) identifies the current increment as Phase 3, while the platform capability API reports Phase 5 and Phase 5 documentation describes end-to-end integration.
4. **Compose health status is not reliable under the inspected run.** Docker's health history shows repeated five-second timeouts for the three demo containers. Direct HTTP `/health` calls returned `UP`, sampling rates were 1.0, and fault modes were `none`. The underlying reason for the timeout was not isolated; do not treat these containers as Docker-healthy.
5. **Current resource snapshots are not an overhead experiment.** A one-time `docker stats` snapshot during this review showed Kafka at 98.71% CPU and 610 MiB of 768 MiB; the backend at 21.63% CPU and 333.8 MiB of 768 MiB; and ML at 0.44% CPU and 146.7 MiB of 1 GiB. These are transient container readings during a test session, without a controlled baseline, sampling window, attribution, or uncertainty. They are **not** resource-consumption results for the platform or adaptive controller.
6. **Prometheus history is not labeled ground truth.** The export/preparation scripts can prepare actual telemetry features, but real unlabeled data is not used to report model accuracy. The evaluated labels come from the deterministic generator.
7. **The service-fault harness is intentionally narrow.** It supports normal, one-second latency, HTTP error, and a bounded 20 ms CPU workload. The Phase 5 scenario script does not implement database slowdown, memory pressure, gradual degradation, or telemetry loss/delay/noise end-to-end.

## 6. Fair baseline comparisons and metric definitions

All comparisons must use the same time range, workload seed, fault timing/severity, service topology, machine/container limits, telemetry sampling, and observation windows. Use paired workload runs where possible, randomize run order, repeat with multiple seeds, and report confidence intervals. Preserve failures and incomplete runs rather than replacing them with inferred values.

### Prediction

- **Baselines:** (1) static p95 threshold alert at the operational threshold; (2) current-value persistence, which is the existing simple baseline; optionally a seasonal/last-value forecaster.
- **Protocol:** Freeze model/features/threshold on training and validation windows. Evaluate on later contiguous windows with rolling-origin splits. Keep each injected event wholly in one split and remove labels crossing split boundaries.
- **Metrics:** `precision = TP/(TP+FP)`, `recall = TP/(TP+FN)`, `F1 = 2PR/(P+R)`, `FPR = FP/(FP+TN)`. Define warning lead time as event onset minus first alert before onset; report missed events separately. For continuous forecasts, report MAE (mean absolute predicted-vs-observed error) and a scale-aware metric; for probabilities, include Brier score and reliability/calibration plots.
- **Uncertainty:** Bootstrap by incident or contiguous time block, not individual minute rows, to avoid treating autocorrelated samples as independent.

### Root-cause ranking

- **Ground truth:** For controlled runs, record the single injected root service/dependency and injection start/end in an immutable scenario manifest. Also include ambiguous/multiple-fault scenarios as a separate task, not as single-cause ground truth.
- **Baselines:** Dependency-blind ranking by largest normalized metric deviation; a second baseline may add log error count without trace edges. Compare against full metric + trace + log + temporal ranking.
- **Metrics:** Top-1 accuracy; `Recall@k` if the known injected cause is in the top k; `MRR = mean(1/rank_of_true_cause)`; optionally NDCG for graded labels. Report per-fault-family results and confidence intervals.
- **Protocol:** Inject one fault at a time, repeat across services and severity levels, preserve the same telemetry volume and query window, and ensure the cause is not leaked as an input feature.

### Adaptive telemetry

- **Baseline:** Fixed trace sampling rate under the same arrival pattern and fault injection as adaptive mode. Keep retention, collectors, exporter queues, service CPU limits, and traffic constant.
- **Metrics:** Collected spans/bytes; exporter/network throughput; CPU and peak RSS by component; detection recall, false-positive rate, detection delay, missing spans/data loss; and the fraction of time within declared CPU/memory/latency budgets.
- **Protocol:** Run paired fixed/adaptive trials across normal and incident periods with predefined seeds. Report warm-up and steady-state separately. Do not equate fewer sampled spans with lower CPU, memory, or storage without direct measurements.

### Investigation workflow

- **Baseline:** Separate Prometheus, Loki, and Jaeger navigation with the same incident packet and service permissions.
- **Metrics:** Elapsed time to identify the known cause, number of manual navigation/actions, final diagnosis correctness, and confidence if collected using a fixed rubric.
- **Protocol:** Within-subject crossover or randomized assignment; counterbalance order and scenario; use the same scenario difficulty and training. Report participant count, experience, exclusions, medians, and uncertainty. Until this is done, MTTR reduction is **Not evaluated**.

## 8. Limitations and threats to validity

- **External validity:** All model labels are generated synthetically. Three demo services and controlled fault shapes do not represent diverse production workloads.
- **Construct validity:** Sampled spans are a telemetry-volume proxy, not resource overhead. Pointwise model metrics do not measure business impact, calibrated risk, alert usefulness, or MTTR.
- **Internal validity:** Existing reports use a single deterministic dataset/replay seed and do not provide confidence intervals. The Phase 5 latency mix combines unlike endpoints and deliberate errors. The review's Docker healthcheck timeouts were not isolated from host/container resource contention.
- **Temporal validity:** A single global chronological holdout is stronger than random shuffling but does not establish robustness across seasons, versions, deployment changes, or unseen services. Forecast probabilities have no calibration report.
- **Label validity:** Synthetic failure intervals are known by construction. Real operational labels can be delayed, incomplete, or ambiguous; there is no real incident ground truth in this environment.
- **RCA validity:** Candidate scores are heuristic, hand-weighted, dependent on supplied evidence, and observational. Correlation/trace ancestry does not prove causation. No ranking baseline or ground-truth quality result exists.
- **Adaptive validity:** The controller changes only demo SDK trace sampling. It does not adjust scrape intervals or control a production Collector. The replay's detection rule is a sampled-error threshold, not the platform's full analysis pipeline.
- **Workflow validity:** No operator study has measured time, steps, correctness, or usability. Incident list/get is not incident lifecycle management.
- **Deployment validity:** Kubernetes is an app-tier scaffold dependent on external services and secrets; no cluster deployment, capacity, network-policy, storage, or rollback test was possible.
- **Test validity:** Unit and component suites pass, but full browser E2E, soak, recovery under collector/store outages, sustained ingestion, and resource-attribution tests are absent.

## 11. Likely viva questions and accurate answers

**Q: What is the main technical contribution?**  
A: The project integrates telemetry collection, timestamp-aware synthetic-data model evaluation, evidence-ranked RCA, and bounded demo trace-sampling control in a local microservice demonstrator. The current evidence does not establish a novel algorithm or production effectiveness.

**Q: Does the forecasting model outperform a baseline?**  
A: Not in the saved synthetic holdout. The Random Forest exactly ties the current-latency persistence/threshold baseline on all reported classification counts and metrics.

**Q: Why use Isolation Forest if the statistical baseline is better?**  
A: It is included as an evaluated ML comparator, not claimed as superior. On this holdout it has perfect recall but substantially more false positives and lower F1. The simpler statistical baseline is stronger on the measured F1/FPR trade-off.

**Q: Are forecast probabilities calibrated?**  
A: Calibration was not evaluated. They are model outputs and should not be interpreted as guaranteed probabilities for real production incidents.

**Q: Does RCA identify the true root cause?**  
A: It ranks candidates from supplied metric deviations, trace ancestry, logs, and temporal evidence. It does not establish causality, and quality against known ground truth has not been measured.

**Q: What does the adaptive controller actually change?**  
A: It changes the OpenTelemetry SDK trace-sampling rate on the local demo services within fixed bounds. Prometheus scrape intervals remain fixed; production collector actuation is not implemented.

**Q: Does adaptive sampling reduce CPU or storage overhead by 61.24%?**  
A: No. That number is the reduction in a synthetic sampled-span-count proxy during a deterministic replay. CPU, memory, network, and storage savings were not measured.

**Q: How was future leakage controlled?**  
A: Features use current/past observations; the dataset is split chronologically; preprocessing is fitted on training data; and forecast training excludes the five-minute label-overlap boundary. This reduces known leakage paths but a single synthetic holdout is not broad validation.

**Q: What incidents are stored and investigated?**  
A: Anomaly and forecast outputs are persisted. RCA candidates are returned to the UI but are not persisted as RCA records or promoted into incidents. Incident history is currently read-only.

**Q: Is the system production-ready?**  
A: No. The system is a local demonstrator. Real incident data, resource/throughput validation, robust production actuation, full incident lifecycle, and Kubernetes rollout validation remain outstanding.
